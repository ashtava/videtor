# Architecture review (2026-11-11)

Asked for by the user: audit the codebase, review the architecture, and say how it becomes a product that
sustains itself and automates more of the editing. This is a review only; nothing in the code was changed.
Where a finding was already in `docs/status.md`, it says so.

Read for this: every module's outline, and in full `cli.py` (the cut), `plan/fill.py`, `plan/shotmap.py`,
`plan/taste.py`, `plan/draft.py`, `ui/server.py`, `ui/jobs.py`, `mcp_server.py` (the cut), `kb/footage.py`
(identity), `plan/library.py` (candidates). The suite was run: 330 tests pass.

## The verdict in five lines

1. **The engine is sound.** Reading footage, choosing a shot for a slot and writing Premiere XML are careful,
   documented and tested module by module. Keep them.
2. **The cut has no home.** The steps of a cut are written inside the terminal command, so the app, the MCP
   server and the three kinds of cut each carry their own copy or scrape the terminal's text. Most of the
   bugs of the last two weeks come from this.
3. **Nothing teaches it.** Four learners exist and none has seen one of the user's fixes: 10 deliveries, 3
   verdicts in words, 0 read-backs. A tool that sustains itself has to collect feedback without being asked.
4. **Nothing measures it.** Tests check that the code runs, not that the cuts got better. A change can make
   every cut worse and all 330 tests still pass.
5. **The judgement is still Claude's, by hand.** The plan and the second look need a live session each time.
   Today's two sports reels needed the draft rewritten, two repeats fixed and a day shot removed from a night
   section, all by eye.

## What holds up

| Part | Why it is good |
|---|---|
| The staged reading of footage (index → keyframe map → full map) | Cached per take, resumable, sized to the machine; a shoot is readable in minutes |
| `plan/fill.py` | One scale for every score (pool z-scores), one assignment over all slots, reasons in words on every pick |
| `export/xmeml_writer.py` and the verified Premiere facts | Hard-won and written down; the round trips are in `out/` |
| The shot map as the one hand-off from judgement to code | Everything after it is deterministic, so a cut can be rebuilt |
| Jobs as separate processes, the cut first | The app stays responsive and a crash takes one job, not the app |
| The docs (`status.md`, `architecture.md`, reports per delivery) | A new session can pick up the work; rare in a project this young |

## Findings, in order of what they cost

### 1. The cut pipeline lives in the terminal command

- **Where:** `cli.py:1003` (`cut`, about 90 lines of steps), `cli.py:1117` (`cut-interview`), `cli.py:1222`
  (`cut-mv`), each with its own `_write_*`.
- **What follows from it:**
  - `mcp_server.py:451` is a copy from Round 4 with no SFX, keeper, taste, effects, accents, medley or byte
    levels (already in `status.md`).
  - The app can only run `videtor cut`, so it can't cut an interview (already in `status.md`).
  - `ui/server.py:192` imports the terminal's private helpers.
  - The effects bug found today (a slot's own `effects` never reach the cut) sits in the glue between `fill`
    and `fx.apply`, which no test runs: the only terminal function the tests call is `_medley`.
- **Fix:** a `videtor/pipeline.py` that owns the steps: `prepare(project)`, `cut(project, plan)`,
  `look(project, choices)`, `readback(project, source)`. Each takes typed inputs and writes one artifact. The
  terminal, the app and the MCP server become thin callers of the same four functions, and one test cuts a
  synthetic project end to end. **Size: medium** (it is a move, not a rewrite).

### 2. The stages talk through loose files and printed text

- **`picks.json` grows by hand.** `cli.cut` copies map settings into it one key at a time (`sfx_skip`,
  `stabilize`, `under_db`, `beds`, `flashes`, `music`); a key nobody copies is silently lost. That is the
  effects bug.
- **The app reads progress by pattern-matching the terminal's sentences** (`ui/jobs.py:32` `STAGES`, `:45`
  `COUNT`, `:27` `SPOILT`). Rewording a print breaks the progress bar or marks a good job as failed.
- **A re-cut forgets decisions.** Second-look swaps live only in `picks.json`, which the next cut overwrites
  (the docs tell every session to apply them again by hand).
- **The shot map accepts unknown keys.** A misspelt option is ignored without a word.
- **Fix:**
  - One function carries a map's settings into the picks, and the picks get a version and a check on load.
  - The pipeline emits events as JSON lines (stage, done/total, file written, warning); the terminal prints
    them as sentences, the app reads them as data.
  - Decisions go in `out/<name>/decisions.json` (swaps, notes, pins) and every cut replays them.
  - `validate` reports keys it doesn't know.
- **Size: small to medium.**

### 3. The learning loop has never turned

- **The state:** `kb/feedback/` is empty and there is no `kb/taste.json`. The keeper exists for one bucket
  (event). The sports cut today printed "keeper: no model for bucket".
- **Why:** feedback needs the user to export an XML or the Premiere bridge to be up (it failed to connect in
  this session), and then someone to run two commands. The app has no place for a verdict at all.
- **Four learners, four formats:** taste (pairs from fixes), keeper (kept against left out), the library
  sorter (folder moves; the only one that has learnt from the user), the sports policy (reels). Each has its
  own files and its own command.
- **Fix, cheapest first:**
  1. **Read the final render back.** `kb/render.py` already splits a finished video into shots. Matching each
     shot to the footage map (CLIP on the frame, then the nearest second) says which picks were kept, slipped
     or replaced, with no export and no bridge. The user renders every job anyway.
  2. **A verdict in the app:** per cut, good or not and one line; per slot, keep or swap. Each click is a
     training pair.
  3. **One feedback store** (`kb/feedback/<project>.json`: slot, what was shown, what was chosen, source) that
     all learners read, and one `videtor learn` that refits what has new data.
  4. **Taste per bucket,** not one global set of weights: an interview and a hype reel reward different things.
- **Size: medium.** This is the item that makes the tool improve on its own.

### 4. No measure of quality

- **The state:** unit tests on synthetic footage. `plan/benchmark.py` can score a cut against a real edit, but
  nothing runs it. Git history is 23 commits named "Auto-save: …", so a regression can't be traced.
- **Fix:** an evaluation set from what is already on disk. For each past edit with a mapped shoot (Guru,
  Diwali, TPL, Alpha Summit, colourstone): its shot map, the cache, and the user's own edit. One command
  re-cuts all of them from the cache (no drive) and reports, per project, takes in common with the real edit,
  the keeper's score, pace against the bucket and repeats. A change to scoring or learning ships only if the
  numbers hold. The same set tells whether a new learner helped.
- **Size: small** (the parts exist), and it should come before any change to how shots are chosen.

### 5. Planning and the second look are not automated

- **The drafter doesn't look at the footage.** `plan/draft.py:78` draws content from the bucket's reels, so
  today it asked for a studio portrait, a drone shot and a team bus that this shoot doesn't have. The whole
  draft was rewritten by hand.
- **The filler judges each slot alone.** Outside a match-cut section, `fill.py:488` assigns takes with no
  term between neighbours. So the same take lands twice in a row, a flicker borrows a day shot for a night
  section, and two takes of one setup sit side by side. Each of those is today a second-look fix by eye.
- **Fix:**
  - **An inventory-aware drafter:** group the shoot into setups (the overview already does), label each from
    the keyframe map, and give slots to what exists, in the bucket's proportions and in shoot order.
  - **Neighbour terms in the filler:** a cost for the same take or setup next to itself, for a jump in light
    (day to night) inside a section, and flickers drawn from their own section. `match_run` already searches
    a run of slots this way; widen it.
  - **A director interface** with three implementations: Claude in a session (today), Claude run headless from
    the app (decision D1), and the offline drafter. The pipeline doesn't care which wrote the plan.
- **Size: medium to large;** it is offline step 1 from `status.md`, with a sharper shape.

### 6. Identity and storage

- **A take's id is a hash of its path** (`kb/footage.py:76`). If a drive is renamed, remounted as
  "Paritosh_2 1", or the footage is copied, every cache entry for it is orphaned: hours of decoding.
  **Fix:** id from size, modified time and a hash of the first and last megabyte, with the path as a lookup.
- **Code, knowledge and projects share one public repo.** `kb/` and `.xml-exports/` are the user's data and
  are tracked; `out/` and `cache/` sit inside the checkout; commands assume the repo is the working folder.
  The user chose to keep the repo public, and this is not about that choice: a second user, a second Mac or
  a packaged app all need the data to live outside the code. **Fix:** one workspace folder
  (`~/Movies/Videtor` or `VIDETOR_HOME`: `kb/`, `projects/`, `cache/`); the repo holds code and tests only.
  This also settles decision D3.
- **Size: small** for the id (with a one-time rename of cache files), **medium** for the workspace.

### 7. The app's local server trusts any caller

- **Where:** `ui/server.py:635`. It checks no Host or Origin header and needs no token, and it reads the body
  as JSON whatever its type.
- **What it means:** while the app runs, a web page open in any browser on the Mac can send it requests:
  start jobs, write a project's brief and plan, move library links, and read files under the allowed folders.
- **Fix:** accept only requests whose Host is the local address, require a token made at launch and sent as a
  header by the page, and require `application/json`. **Size: small.** Do this before anyone else uses the app.

### 8. The cut decodes more than it needs

- **`skip` is ignored when choosing what to decode** (`plan/library.py:721`): reel A today named its takes
  and skipped the other shoot, and all 87 takes were decoded (595 s) where 46 were needed.
- **No shortlist:** the cut narrows by class only (already in `status.md`). The keyframe map could rank takes
  per slot first and decode the top few.
- **Fix:** apply `skip` in `candidates`; then shortlist per slot from the keyframe map. **Size: small**, then
  **medium**.

### 9. Surface to trim

| What | Detail | Action |
|---|---|---|
| Rounds 1-3 code | `plan/rules.py`, `structure.py`, `rerank.py`, `benchmark.py` and the commands `plan`, `export`, `analyze`, `ingest`, `kb rerank-eval`: about 1,400 lines | Move to `scripts/archive/`, keep `benchmark.score_picks` |
| The MCP server | 652 lines, behind the terminal since Round 4; the user chose the app | Rebuild as a thin caller after finding 1, or remove |
| Dependencies | `mcp` and `otio-fcp-adapter` in the core list; Python pinned to 3.11 only | Move `mcp` to an extra; drop the adapter if the archive goes |
| No checks before a push | The hook pushes every turn; no tests, lint or types run | Run the suite (14 s) in the hook; refuse to push on failure |
| Commit messages | "Auto-save: files…" | Let the hook take a one-line summary from the session |
| Hand-set weights | The 0.8, 0.6, 1.2 in `fill.sample_scores` | Name them in one table per bucket; let taste correct them per bucket |
| One embedding model | CLIP ViT-B/32, 512 wide, assumed in `fill.py:127` | Read the width from the map; the stills are cached, so a better model can re-embed with no drive |

## The shape to aim for

```
front doors (thin)     terminal · app · MCP · scheduled runs
                          │ call                ▲ events (JSON lines)
pipeline (one home)    prepare → plan → cut → look → export → readback
                       each step: typed input → one artifact on disk, resumable, replayable
director (pluggable)   Claude in a session · Claude headless · offline drafter
workspace (data)       ~/Movies/Videtor/{kb, projects, cache}      (the repo holds code only)
learning               feedback store ← final render · XML · in-app choices
                       → learners (keeper, taste, sorter, policy) → evaluation on past edits → promote
```

Two rules keep it honest: a front door never contains a step, and a learner's new model is used only after the
evaluation set says it did no harm.

## What it could automate after that

Each of these is cheap once phases 1-3 are in, and each saves editing time on every job.

- **Versions to choose from.** Cut three variants (music, seed, pace) and let the user pick. The pick is also
  the cheapest feedback there is.
- **Other aspect ratios from one cut.** The picks already carry reframing; 9:16, 1:1 and 16:9 are the same
  picks built three times.
- **Captions and word cards.** Whisper gives word timings, and Premiere's XML import translates text
  generators (in the verified table, not yet tried).
- **Bytes picked automatically.** Rank spoken lines by loudness edges, length and the brief's words; today
  Claude picks them by hand.
- **Ingest on arrival.** A watched folder or drive: a new card is read overnight and the overview is waiting,
  with a Mac notification.
- **A Resolve hand-off.** The timeline already exists as OpenTimelineIO in `plan/build.py`; Resolve imports
  `.otio`. Motion and effects would need checking there.
