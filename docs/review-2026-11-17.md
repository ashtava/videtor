# Audit, 2026-11-17: the state machines nobody wrote down, and where the time goes

Asked for by the user: "find all the implicit state machines in my app and fix them; review the architecture for
any unoptimisations and create a fix; a plan first, then subagents in parallel." This is the audit and the plan.
The work is done in six packages, one owner each, on the branch `refactor/state-machines`; `main` gets it when the
whole suite, the evaluation and the pick-for-pick comparison pass.

An implicit state machine here means: a thing that is always in one of a few states, where the states and the
moves between them are not written down in one place but spread over string comparisons, file-exists checks and
flags, in several files that have to agree. Two of the three bugs of 11-16 were exactly that (a cut crashed because
six phases of the fill shared an unwritten rule; a failed promo run looked like a wrong result because "running",
"failed" and "what is on the page" were three separate ideas).

## How it was done

Read: `ui/jobs.py`, `ui/server.py`, `ui/static/app.js`, `pipeline.py`, `plan/edit.py`, `plan/fill.py`,
`kb/feedback.py`, `teach.py`, `plan/evaluate.py`. Counted where the code branches on a status, a kind or a file.
Timed the running app's endpoints, the commands' start-up, and one cut under the profiler. Cut every evaluation
project twice with today's code: the picks are byte-identical run to run, so "nothing changed" can be proven
(`scripts/picks_snapshot.py`).

## Part 1: the state machines

### S1. A job (`ui/jobs.py`) — package A
- **States:** queued, waiting, running, paused, done, failed, cancelled, plus the flags `paused_by`, `was_paused`,
  `reran_as`. The strings are compared in 31 places in `jobs.py`, 16 in `server.py`, 26 in `app.js`.
- **Moves** are made in six methods (`submit`, `_start`, `_finished`, `pause`, `resume`, `cancel`), each writing
  `job.status` itself. The "a cut gets the machine" rule is spread over three of them.
- **What can go wrong:** nothing stops two jobs that write the same project's cut (a cut and a "write the XML", or
  two cuts: only the page's greyed-out button does); job ids start again at j1 on every launch, so a page left open
  can show another job's status; jobs live only in the app's memory, so a job left running by a crash is unknown to
  the next launch, which may start a second one on the same caches.
- **Also here:** the stage shown for a job is guessed from its output with eleven regular expressions (`STAGES`),
  for the commands that still print sentences (S8).
- **Fix:** a `Status` enum with the sets `LIVE`, `ALIVE`, `ENDED`; one table of allowed moves and one method that
  makes them; `writes` on a job and a `Busy` error when a project already has a writer; ids unique across launches;
  a record of running jobs on disk so a launch can stop what the last one left behind; `live`/`ended` in every job
  the server sends, so nobody else compares strings.

### S2. Where a project stands (`ui/server.py`, the page) — package B
- **States:** footage not read, needs the brief, needs the plan, plan has problems, ready to cut, cut ready, and
  on top of those: the drive connected or not, a job running, the kind of project (a cut, an interview, a music
  video). Decided by 31 file checks in `server.py` and 15 in `pipeline.py`.
- **Written four times, in four orders:** `_status` (the card), `_steps` (the steps and "next"), `api_cut` (what a
  cut needs), and `renderCutTab` in the page (when the Cut button is live). They agree today by care.
- **What can go wrong:** any of the four drifting; a step started by an endpoint that the page would have refused.
- **Fix:** `videtor/project.py`: one reading of a project's folder into a `Project` (its stage, its facts), one
  `can(action)` that says yes or why not in words. The server's card, steps, "next" and every endpoint's refusal
  come from it; the page is sent `can` and stops deciding.

### S3. The cut as a document (`pipeline.py`, `plan/edit.py`) — package D
- **States:** as cut, edited (changes not in the XML), written. Three files move together: `picks.json`,
  `decisions.json`, `work/history/`.
- **How it is known today:** "edited" is `picks.json` newer than the XML by more than a second (`edit.timeline`).
  The three files are written one after another, each in place.
- **What can go wrong:** a clock, a copy or a drive with coarse timestamps makes a written cut look edited or the
  reverse; a failure between the writes leaves picks that the decisions do not describe; an edit made in the app's
  own process can cross a job writing the same file (S1's `Busy` closes that).
- **Fix:** the XML's writer records which picks it wrote (`work/xml.json`: a hash); "edited" is "the picks are no
  longer those"; the three files are committed together, each written whole and swapped in.

### S4. Kinds of cut and kinds of slot — package D
- **Cut:** a plain cut, an interview, a music video, a promo. `look` finds out with
  `picks.get("kind") == "music-video"`, then `(picks.get("source") or {}).get("aroll")`, else plain.
- **Slot:** shot, ramp, flicker, stack, byte, black, empty, read off the flags `byte`, `pick.pieces`, `pick.ramp`,
  `layers`, `black`. `plan/edit.kind` says it once; `build._v1_clips`, `export/proxy`, `export/preview`,
  `export/promo`, `kb/renderback` and others read the flags again (19 files branch on them).
- **Fix:** `plan/slots.py` owns a slot's kind, what can be done to it and the clips it plays; `pipeline` owns a
  cut's kind and a table of how each kind is rebuilt. The old names stay as aliases.

### S5. The fill's assignment (`plan/fill.py`) — package E
- **State:** which take each slot has (`chosen`), through six phases: the assignment, the plan's named takes, the
  windows of a take used twice, match-cut runs, the neighbours, the fallback.
- **The unwritten rule:** `chosen[j] = k` only if `(j, k)` was scored (`detail` has it, `S[j, k] > -1e5`). The
  crash of 11-16 (`KeyError: (19, 7)`) was one phase breaking it.
- **Fix:** one small object holds `S`, `detail` and `chosen`, and the only way to give a slot a take checks the
  rule. No change to what is chosen (proven pick for pick).

### S6. A feedback document (`kb/feedback.py`, `kb/readback.py`) — package F
- **States of a row:** kept, slipped, trimmed, swapped, swapped_to_alternate, removed ... as strings written in
  `readback.py` and read in `feedback.py`, `taste`, `teach` and the page. **States of a document:** empty, choices
  only, a verdict only, a finished job read back, a job cut by hand, suspect: found out by `is_final` and friends.
- **Fix:** the row statuses named once and imported; one function that says what a document is.

### S7. The page (`ui/static/app.js`) — package C
- **A panel with a job:** idle, running, done, failed. Twelve places start a job and watch it; several show
  nothing when it fails (the read-back and "learn" buttons only fill a log). The promos page got the explicit
  version on 11-17; the others did not.
- **An answer that comes late:** only `loadProject` checks that the project it asked about is still the one open.
- **Its own copy of the rules:** `LIVE` (S1), the Cut button (S2).
- **Fix:** one helper for a panel's run (what is shown is dimmed and said to be older while it runs; a failure is
  said, with the reason, beside the button that started it); a late answer is dropped everywhere; `job.live` and
  `project.can` are the server's.

### S8. Steps that print instead of reporting — package D (and A)
`library build`, `library learn` and the old `preview` are not steps of `pipeline.py`; they print sentences, and
`jobs.py` guesses their stage from the text. **Fix:** they become steps that report through `events`; the eleven
expressions go.

### Looked at and left as they are
- **The timeline's player:** two states (stopped, playing), three functions that own every move (`tlPlay`,
  `tlStop`, `tlSeek`). Tuned on 11-16; not touched.
- **Promo sets:** made explicit on 11-17 (a set per making, the page opens the set the job made).
- **Prep's caches:** each pass asks its own `is_done`; resumable by design.
- **The library's moved links:** read off the folders, because Finder is the editor.
- **The music setting's three states:** validated in one place (`plan/settings.validate`).

## Part 2: where the time goes (measured on this Mac)

| | What | Measured | Fix | Package |

Documentation (`README.md`, `docs/`, `CLAUDE.md`) is the integrator's: packages report what changed and edit none.

### Contracts between packages (code to these, even before the other side lands)

1. **Jobs (A gives; B and C use).**
   - `class Status(enum.StrEnum)` with the seven values spelled as today (`"running"` ...), so `job.status ==
     "running"` and JSON are unchanged. `LIVE = {WAITING, RUNNING, PAUSED}`, `ALIVE = {RUNNING, PAUSED}`,
     `ENDED = {DONE, FAILED, CANCELLED}`.
   - `Manager(videtor, cwd, log=None, env=None, record: Path | None = None)`: `record` is the file where running
     jobs are noted; a launch stops what an earlier launch left running and says so in the log.
   - `Manager.submit(kind, title, args, project=None, writes=False)`. With `writes=True` it raises
     `jobs.Busy(job)` (a `RuntimeError` with `.job`, the job in the way) when the project already has a live writer.
     `Manager.busy(project) -> Job | None` answers the same question without submitting.
   - `Job.to_dict()` gains `"live"`, `"ended"` and `"writes"`. Ids still match `j\d+` and never repeat across
     launches.
2. **Projects (B gives; C uses).** `/api/project` gains `"stage"` (`footage`, `brief`, `plan`, `cut`, `review`)
   and `"can": {"prep" | "cut" | "edit" | "look" | "write_xml" | "readback": {"ok": bool, "why": str}}`. Every POST
   that starts one of these answers `{"error": why}` when `ok` is false. B passes `writes=True` for jobs that write
   a project's cut (cut, look, write-xml) and refuses `api_edit` while such a job is live.
3. **The page (C)** reads `job.live` and `p.can` when they are there and falls back to what it does today when
   they are not, so it works against either server.
4. **Slots and cuts (D gives).** `plan/slots.py`: `kind(slot)`, `plain(slot)`, `can(slot, next_slot) -> dict`,
   `clips(slot, fps)`, `own_sound(slot)`. `edit.kind`, `edit.plain` and `build._v1_clips` stay as names. No public
   function of `pipeline.py` changes its signature. The timeline's answer keeps `dirty` and `has_xml`.
5. **Feedback (F gives).** The statuses keep their spellings; documents on disk are read and written as before.
6. **Fill (E).** `fill.fill`, `fill.Pool`, `fill.sample_scores`, `tags.embed_texts` keep their signatures.

### Rules for every package
- The repo's own rules stand (`CLAUDE.md`): compact Python, a docstring that says what a module is for in plain
  words, `unittest` with made-up fixtures, steps report through `events`, no install, no footage opened, nothing
  of a client's in a tracked file.
- Run your own tests often. Other packages are being written in this same folder at the same time: a failure in a
  file you do not own is theirs. Wait, run again, and report it if it stays; do not fix it.
- Never start the real app or use port 8765, and never write into a project folder under `out/` or on a drive.
  Checks that need a project use a copy in a temporary folder.
- Do not commit. Report: what changed, what was run and what it showed, what is unverified.

### Integration (after the six report)
1. The whole suite; `videtor eval`; `scripts/picks_snapshot.py --compare` against the snapshot taken before any
   package started (all nine identical, or the difference explained and accepted by name).
2. Every past project's XML rebuilt from its picks and compared with the XML on disk.
3. The page driven in headless Chrome: a project's steps, a cut refused in words, the timeline (edit, undo, write),
   promos (a run, a failed run), Teach.
4. `README.md`, `docs/architecture.md`, `docs/status.md`, `CLAUDE.md`; then `main`.
